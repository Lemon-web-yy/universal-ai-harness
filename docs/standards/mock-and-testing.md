# 架构隔离式 Mock 与测试规范

> **定位：** 本治理框架的测试策略总纲。
> **核心思想：** 不引入 mock 框架，**用架构隔离代替 mock 桩**——被测模块零平台依赖 + 依赖以回调/函数指针注入，从而在开发机上直接编译运行真实代码。

## 1. 为什么是"架构隔离"而不是 mock 框架

| 对比项 | mock 框架 | 架构隔离式 |
|--------|-----------|------------|
| 依赖 | 第三方库 | 无 |
| 维护成本 | 接口变更需同步 mock | 无 mock 可失效 |
| 测试的是 | mock 的行为 | **真实代码** |
| 前提 | 无 | 分层纪律（见下） |

**架构前提（本来就该有的纪律，测试只是顺带受益）：**

1. 业务模块（L3）不直接调用平台/驱动 API（L1），依赖通过：
   - 回调注册注入（`xxx_set_callback(cb, user_data)`）
   - 接口结构体/函数指针传入（init 时注入）
2. 协议解析是纯函数：输入字节流/消息，输出结构体+回调，无 I/O
3. 算法模块无副作用无全局变量（可直接测）
4. 状态机逻辑与副作用出口分离（周期函数是唯一副作用出口 → 主机测试只调状态 API 断言）

## 2. 可测性分层表

| 层 | 主机可测 | 测法 |
|----|----------|------|
| 纯算法 | ✅ | 直接编译跑 |
| 协议/消息解析与打包 | ✅ | 喂字节流/消息，断言回调/输出 |
| 业务状态机/消抖/互锁 | ✅ | 调状态 API + 手动推进伪周期，断言状态 |
| 适配器语义翻译 | ✅ | 喂 raw 事件，断言统一事件 |
| 平台驱动（I/O/系统调用/外部服务） | ❌ | 真实环境验证 |
| UI 渲染 | ❌ | 人眼/真实环境验证 |

## 3. 单测文件规范

- 命名：`<module>_test` 后缀，与被测模块一一对应
- 框架：语言自带断言（如 C 的 `assert.h`、Python 的 `assert`）+ 自造 CHECK 宏（无需外部依赖）：

```c
#define CHECK(cond) do { \
    if (!(cond)) { \
        printf("FAIL %s:%d: %s\n", __FILE__, __LINE__, #cond); \
        g_failures++; \
    } \
} while (0)
```

- 文件头注释写明**编译/运行命令**（复制即用）
- 结构：入口函数内多个 `test_<场景>()` 函数 + 末尾汇总 failures 计数，非零退出码（可接 CI）

## 4. 测试桩（stub）使用规范

当被测模块确需外部依赖时（如需要系统调用/外部服务），**优先重构解耦**；确需桩时：

- 桩文件命名 `stub_<依赖>`，只实现被测模块声明的接口
- 桩行为：计数调用 + 可编程返回值（全局变量设定），**不模拟真实时序**
- 桩必须在 ADR 中登记（防止桩与真实实现漂移无人知）

## 5. 禁止事项

| # | 禁止 | 防止什么 |
|---|------|----------|
| 1 | 为可测性在业务代码里加 `#ifdef TEST` 分支 | 生产/测试代码路径分叉，测的不是上线的东西 |
| 2 | mock 桩模拟真实时序/网络延迟 | 时序问题只能在真机暴露，假时序给虚假信心 |
| 3 | 单测依赖执行顺序/共享可变全局态 | 测试不可重复，偶发失败无法定位 |
| 4 | 测 getter/setter 这类无逻辑代码 | 假覆盖率，浪费维护成本；只测有分支/边界的行为 |

## 6. 验证三层金字塔

```
        ┌─────────┐
        │ 真实环境 │  ← 用户做（部署+真实场景）
        ├─────────┤
        │ 集成验证 │  ← agent 驱动（数据流穿通多端）
        ├─────────┤
        │ 单元测试 │  ← agent 做（本规范，每次收尾跑全绿）
        └─────────┘
```

单元测试全绿 ≠ 可用，但单元测试红 = 一定不可用。收尾归档前单元测试必须全绿并记录到 progress.md。
