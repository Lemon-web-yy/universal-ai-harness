# 跨模块变更工作流（L0-L3 评级分段）

> **定位：** 需求涉及 2+ 模块时的协同流程（agent 执行参考）。单模块需求不走本流程。
> **通用化：** 本工作流不依赖任何特定技术栈，适用于任意语言与架构的跨模块协同。

## 评级判断（第一步，决定流程重量）

| 评级 | 联系方式 | 流程 | 举例 |
|------|---------|------|------|
| **L0 纯独立** | 各模块自己干 | 不走跨模块流程，按模块 CLAUDE.md | 模块内部重构 |
| **L1 契约同步** | 发布契约到 `.harness/contracts/`，按需订阅 | 只定契约不派发 | A 模块发布新接口，B 模块按需读取 |
| **L2 协调开发** | Coordinator 轻度协调，并行实现 | 定契约+并行派发+架构审核+收尾 | 跨 2-3 模块的功能集成 |
| **L3 统一编排** | Coordinator 全程主导 | 完整流程 | 跨全部模块的大型变更 |

**评级依据：** 联系强度 = 需求涉及几个模块 + 是否需要接口同步。**能 L0 不 L1，能 L1 不 L2，能 L2 不 L3。**

---

## L1 — 契约同步（3 步）

```
1. Coordinator 写 .harness/contracts/NNN_*.md（5 章节契约档案）
2. 用户审核契约（spec review gate）
3. 各模块按需 Read 契约 → 自己实现（各自走 L0 流程）
```

**关键：** 不派发子 agent，各模块自治。

## L2 — 协调开发（跨 2-3 模块）

### 第一步：根 agent 定契约（此时不写代码）

派发 Coordinator agent，写 `.harness/contracts/NNN_*.md`（用 `_template.md` 的 5 章节格式）。完成后**停下来给用户审**——契约是架构决策，用户不点头不往下走。

### 第二步：并行派发（prompt 只给路径不给全文）

按契约判断实际涉及的模块，派发对应 Builder 子 agent。**仅列实际参与者，不默认列全**（教训 L07）。

每个子 agent 的 prompt 包含五要素：
- 根级契约档案的**路径**（要求自行 Read 完整契约）
- 对应模块的 CLAUDE.md 路径
- **镜像参考模板路径**（要求先读模板再动手）
- 明确的任务边界（"只改 X，不要碰 Y"）
- 引用的教训编号（如"注意教训 L05/L21"）

**单端先行模式合法**（教训 L19）：契约可只覆盖链路的某一段，其余段另开契约。允许先派发一端，另一端后续跟进。

### 第三步：子 agent 自治实现

各 Builder 在各自模块内：写模块 ADR → 按 Scope 实现 → 编译验证（无法编译的标 `[未验证]`）→ 更新模块 .harness/progress.md。

### 第三步半：架构审核（进入收尾前）

派发 Architect-Reviewer agent，按六维清单审核（SRP / DRY / 封装 / 模块边界 / 命名常量 / 档案同步）。**P0 问题必须修复后才能收尾**，P1/P2 可标注延后。

### 第四步：收尾归档

1. 三层验证逐项核对：编译验证（各端独立编译）→ 集成验证（数据流穿通两端）→ 真实环境实测（用户部署真机）
2. 更新 `.harness/contracts/index.md` + 各模块 `.harness/progress.md`
3. 运行 `python .harness/audit_harness.py` 核对索引与实体一致（教训 L22）
4. 边界外问题独立记录到 Known Issues，不阻塞本需求收尾

## L3 — 统一编排（全模块复杂变更）

跟 L2 相同五步，但 Coordinator 全程主导：契约需覆盖全链路分段定位、派发清单列全参与端、每端完成即检查点汇报、收尾需全链路联调节奏表。

## 经验教训（稳定编号，新增追加不重排）

> **机制：** 编号一经分配永不重排，新增教训追加编号。契约/ADR 按编号引用。每条注明"验证状态"。
> **来源说明：** L01-L12 为种子教训（从源工程逆向提炼并通用化），本项目实战后继续追加。

### ✅ 验证有效

- **L01 契约先行有效** — 首次跨模块契约实战即避免两端理解不一致。流程：先档案后代码。
- **L02 评级路由防浪费** — 联系强度定流程重量，避免小需求走重流程。
- **L03 三层验证缺一不可** — 编译过 ≠ 集成过 ≠ 真实环境可用。逐层勾选。

### ⚠️ 待优化

- **L04 契约应包含依赖前置条件** — 契约中明示"依赖 X 模块已就绪"，否则 Builder 实现时才发现依赖缺失。
- **L05 子 agent prompt 给路径不给全文** — 契约是单一真相源，粘贴全文会引入版本不一致。
- **L07 子 agent 按需列** — 默认列全部模块会扩大风险面与审核负担。
- **L22 收尾必跑索引核对** — 索引与实体漂移会让后续 agent 按索引找档案扑空。

### 🐛 测试 bug 类

- **L08 位域映射语义错误** — 位域全组合速查表（2^有效位数 种）能在纸面阶段抓住映射错误，成本远低于真机调试。
- **L09 跨线程数据交接坑** — 线程 A 解析 / 线程 B 消费时，明确连接类型（Direct vs Queued）与数据所有权，否则偶发崩溃难复现。
- **L10 流式数据半包处理** — 流式 IPC/网络读到的可能是半包，必须累积缓冲 + 按分隔符拆包，不能假设一次读一个完整消息。

### 🏗️ 架构审核通用

- **L14 数据归属原则** — 数据映射归数据生产者，通道归通道模块，UI 归独立组件。谁生产谁负责翻译语义。
- **L15 一行搞定原则** — 组装层调用模块 API 应"一行搞定"，暴露内部多步骤说明封装不足。
- **L17 命名常量优于裸魔法数字** — 尺寸/阈值/路径全部命名常量。审核硬项。
- **L23 模块接口镜像同构** — 同类模块的接口结构（枚举+API+常量）应镜像一致，结构差异需在 ADR 说明理由。

### ✅ 可复用模式

- **L19 单端先行模式合法** — 契约可分段覆盖，先做一端另一端跟进，不必等全链路设计完备。
- **L20 "不做的事"是契约关键部分** — 每条不做事带理由，防止子 agent 自由发挥。不是附录。
- **L21 镜像参考模板必须显式标注** — 新增同类模块默认必须镜像已有模板（强制/建议两级），发散的模式难以维护。
