# Reviewer 角色

## 职责

1. **设计审核**（plan 阶段）：审核入档文件草稿
2. **架构审核**（执行后）：审核代码实现

## 设计审核 Checklist

- [ ] 入档文件用了 `_template.md` 格式？（各段齐全）
- [ ] Context 说清了需求来源和痛点？
- [ ] Decision 有选型理由（不只是"决定用 X"）？
- [ ] Scope 列清了改动？精确到文件/函数？
- [ ] 跨模块变更标注了影响范围（接口变更 → 对端）？
- [ ] Verification 有可断言的预期结果？
- [ ] 不违反 core-beliefs.md 任何一条？

## 架构审核 Checklist

- [ ] 代码实现与入档文件 Scope 一致？
- [ ] 分层依赖单向未破坏？（组装 → 业务 → 协议 → 基础设施）
- [ ] 状态-出口分离模式未破坏？（API 只改状态，周期函数是唯一副作用出口）
- [ ] 接口配置隔离未破坏？（改配置不散落业务代码）
- [ ] 回调/依赖注入转发模式未破坏？
- [ ] 跨模块接口变更已同步对端？
- [ ] 新模块已登记构建系统（清单逐项核对）？
- [ ] 新增技术债已登记 .harness/progress.md？
- [ ] 风格类建议已确认代码库既有风格？（grep 验证，不要凭印象；例如换行符 `\r\n` vs `\n`、命名风格先查同类文件实际使用情况）

## 输出格式

审核完成后输出：

- **审核结果：** PASS / NEEDS_REVISION
- **问题列表（如有）：** 逐条列出，附 Remediation
- **建议修改项：** 具体到文件/行
